# v0.23.0-alpha 目标机升级回归诊断与修复设计

日期：2026-08-11

状态：设计已确认，已合入 Issue #25 统一规格

适用版本：AI-WPS `v0.23.0-alpha`

## 1. 现场背景

目标机此前安装过前一版本，并已保存八类任务的工作流平台地址与 API Key。执行 `v0.23.0-alpha` 升级安装后，Word 设置页出现以下现象：

1. 写作规范库显示“暂不可用”，统计为 0 条规范、0 条启用；
2. 新建模型配置填写后不能正常保存，也不能选择升级前保存的工作流配置；
3. 重新进入模型配置页后，“新建模型配置”按钮置灰；
4. 页面明确提示无法访问 `http://127.0.0.1:18100`，要求确认 Adapter 正在运行。

## 2. 当前已确认事实

### 2.1 三组界面异常共享同一上游故障

截图证明任务窗格当时无法访问本地 Adapter。前端在本地连接失败时进入只读快照或未连接状态，因此：

- 不能读取、创建、更新或激活模型配置；
- “新建模型配置”按钮被禁用；
- 不能读取写作规范库摘要；
- 高级诊断无法检测。

所以当前不能把“写作规范库不可用”“模型配置不可保存”“按钮置灰”先判定为三个互不相关的前端缺陷。首要故障是 Adapter 未监听、启动后退出、端口冲突或插件连接到了错误的安装实例。

### 2.2 升级安装会保留运行数据

当前安装脚本会在替换 Adapter 目录前暂存并恢复：

- Adapter 配置；
- 统一及按任务保存的 API Key 文件；
- 写作规范库数据库及其恢复备份。

恢复旧状态后，安装脚本初始化或复用写作规范库数据库，再启动 Uvicorn Adapter，并要求健康检查返回 `0.23.0-alpha`。

### 2.3 前一版本工作流配置需要运行时迁移

模型配置服务首次读取配置时，会将旧工作流配置迁移为 `workflow_platform` 模型配置，并复用旧 API Key 引用；旧激活关系也会迁移为当前激活配置。该迁移依赖旧配置 JSON 可读、配置目录可写、Key 文件仍在预期目录。

### 2.4 当前证据不足以确定 Adapter 失败阶段

截图不能区分以下情况：

- 安装脚本从未成功启动新 Adapter；
- 新 Adapter 启动后因导入、依赖、配置、权限或数据迁移异常退出；
- 旧 Adapter 或其他进程占用 18100，替换未完成；
- Adapter 安装在另一个用户目录，后续启动或 WPS 使用的是不同实例；
- Adapter 曾经可用，但在保存模型配置前后被外部进程终止。

### 2.5 升级执行用户与前序版本一致

用户确认，前序版本和 `v0.23.0-alpha` 都是在登录用户 `cloud` 下直接执行交付包 `installer` 目录中的 `install_phase1.sh`，没有使用 `sudo` 或切换到 `root`。按安装器默认值，Adapter 安装根目录应保持为 `/home/cloud/ai-wps-phase1`。

因此，“本次升级因 sudo 导致 Adapter 安装到 `/root`，而 WPS 插件安装到 `/home/cloud`”可从当前调查主线排除。仍需检查目录所有权是否被更早的安装或人工操作改变。

### 2.6 Adapter 因 Python 3.8 类型注解不兼容而在导入阶段退出

目标机状态脚本报告 Adapter PID 已失效，18100 健康检查和 Provider 状态均不可达。Adapter 日志给出确定异常：

```text
model_configurations.py, line 707
def _platform_configurations(self, task_type: str) -> tuple[dict, list]:
TypeError: 'type' object is not subscriptable
```

目标机使用 Python 3.8。内置容器泛型写法 `tuple[...]` 从 Python 3.9 才可在当前使用方式下运行；该模块没有延迟注解求值，因此 Python 3.8 在导入类定义时立即执行注解并抛出 `TypeError`。Uvicorn 尚未完成应用导入，Adapter 没有开始监听 18100。

仓库生产 Python 代码扫描仅发现这一处内置容器泛型写法。当前兼容写法应使用 `typing.Tuple[Dict, List]`，或采用经项目统一验证的延迟注解方案。修复仍必须在 Python 3.8 上执行完整应用导入，不能只依赖开发机语法编译或 Python 3.9 以上测试。

### 2.7 旧配置和写作规范数据尚未进入运行时迁移

本次异常发生在 `model_configurations` 模块导入期间，早于 Adapter 启动、模型配置首次读取、旧工作流配置迁移和写作规范库 API 调用。因此当前没有证据表明八套旧工作流配置、API Key 文件或写作规范数据库已被应用代码改写或损坏。

安装器确实已完成运行数据的备份与恢复动作，但数据内容是否完整仍需在修复版 Adapter 成功启动后通过只读清单和迁移结果验证。

## 3. 当前根因假设

根因已经由目标机日志确认：发布包包含 Python 3.9+ 才能运行的 `tuple[...]` 类型注解，但目标运行时为 Python 3.8，导致 Adapter 在导入阶段退出。

以下问题仍作为修复后验证分支保留，不再作为本次启动失败的竞争根因：

1. 旧配置迁移后的八类任务数量、地址、Key 引用和激活关系是否完整；
2. 写作规范数据库和预置规范包是否可读取；
3. 安装目录、配置、Key 和 SQLite 文件的所有权与权限是否正确；
4. 修复版是否仍存在其他只能在 Python 3.8 导入或执行时暴露的兼容问题。

## 4. 下一项必需证据

已取得目标机 Adapter 状态和启动日志，确认失败发生在应用导入期间、端口监听之前。下一项证据应来自修复候选包在 Python 3.8 上的应用导入、健康检查和升级数据验证。

## 5. 已确认的产品与修复决策

- 已确认修复与全篇文档审查统一规划和开发，但设置两个可独立验证的交付节点：先交付恢复构建，再交付包含全篇审查的整合版本；
- 已确认采用事务式升级：候选构建在隔离目录通过目标 Python 3.8 完整导入、启动和健康检查后才切换当前安装；失败时保留或恢复旧插件、Adapter 和运行数据；
- 已确认候选代码可以启动、但模型配置或任务路由等核心数据读取/迁移失败时，Adapter 进入恢复模式：进程、健康检查、诊断、备份和显式恢复能力保持可达，但核心业务未就绪；仅写作规范等非核心增强数据失败时进入降级状态，核心 Word 任务按既有规范降级契约继续执行，故障子系统的管理操作禁用；两种状态下原数据都保持只读，不得静默重置、覆盖或删除；
- 核心代码无法导入、候选包完整性校验失败或基础 API 契约不兼容时，不进入恢复模式，而是判定候选构建验证失败，由事务式升级机制保留旧版本；
- 已确认旧模型配置和写作规范数据采用写时复制迁移：先生成原数据脱敏清单和校验信息，在隔离副本上迁移并验证八类任务配置、服务地址、Key 引用、激活关系和规范库完整性，全部通过后才原子切换；任一步失败均保持原数据不变并进入恢复模式；
- API Key 验证仅比较存在性和不可逆指纹，安装、迁移、诊断及验收日志均不得输出明文；
- 已确认恢复构建使用独立版本 `v0.23.1-alpha`，范围包括 Python 3.8 兼容修复、事务式升级、写时复制迁移、恢复模式及升级验收；不得覆盖或重新发布为 `v0.23.0-alpha`；
- 已确认全篇文档审查整合版本使用 `v0.24.0-alpha`，必须建立在已经独立验证通过的 `v0.23.1-alpha` 修复基线上；
- 已确认真实 Python 3.8 运行验证是 `v0.23.1-alpha` 及后续版本的阻断式目标运行时门禁，不得用语法编译、静态扫描或 Python 3.9 以上测试替代；
- 目标运行时门禁必须对最终交付包执行完整应用导入、Uvicorn 真实启动、`/health` 版本和关键配置接口验证，同时覆盖全新安装、携带八类任务配置/Key 引用/规范库数据的 `v0.22.0-alpha` 升级、核心数据损坏进入恢复模式、规范数据损坏进入降级状态，以及不可导入候选包不切换旧版本；任一检查失败均不得标记为可交付；
- 已确认自动化门禁通过后只能标记为 `v0.23.1-alpha` 候选构建；只有在麒麟 V10、目标 WPS 和 `cloud` 登录用户环境完成真实升级验收后，才能标记为已验收恢复构建并宣称现场故障解除；
- 目标机验收至少覆盖 Adapter 持续监听 18100、WPS 重连、原八类工作流配置/地址/Key 引用/当前选择保持、新建保存切换模型配置、写作规范库数量/启用状态/更新时间恢复、WPS 与 Adapter 重启后状态保持，以及日志和验收材料不含 API Key 明文；
- 已确认安装器在任何写入前必须验证安装主体一致性：默认只允许当前 WPS 登录用户以非 `root`、非 `sudo` 方式安装，插件、Adapter 和运行数据目录必须属于同一 UID 且可写；校验失败立即停止并保持原状态，不得静默递归 `chown`；
- 后续如需管理员代装，只能通过显式 `--target-user` 指定用户，并验证目标 UID、主目录及 WPS 插件目录，不能根据 `root` 的 `$HOME` 推断安装位置；
- 已确认健康状态拆分为三层：`/health/live` 只检查进程和基础 Web 应用且不读取业务数据；`/health/ready` 检查核心必需业务子系统；兼容接口 `/health` 返回聚合状态和脱敏子系统状态；
- 聚合状态分为 `ready`、`degraded` 和 `recovery`。规范库等非核心增强子系统单项失败时为 `degraded`，`/health/ready` 返回 HTTP 200，Word 任务按规范降级继续；模型配置或任务路由等核心数据失败时为 `recovery`，`/health/ready` 返回 HTTP 503；三种状态下 `/health/live` 和 `/health` 都返回 HTTP 200；
- 子系统分别报告 `ready | degraded | recovery`、稳定错误码、发生阶段和允许的恢复动作，不得返回 API Key、配置正文或敏感绝对路径；安装器仅拒绝自动切换 `recovery` 候选；前端必须区分增强能力降级和核心恢复模式，不得误报为“无法连接 Adapter”；
- 已确认当前安装已经不可用、但候选只能进入恢复模式时，首次安装命令默认停止切换并保留当前安装和候选隔离目录，同时输出脱敏故障摘要、备份状态和恢复命令；
- 仅当当前版本也不就绪、原数据备份校验通过、候选 `/health/live` 返回 200 且 `/health.status` 为 `recovery` 时，才允许用户通过显式 `--activate-recovery` 激活候选；激活后只开放诊断、备份和恢复能力，结果标记为“已激活恢复模式”，不得标记为升级成功或已验收恢复构建；
- 已确认 `degraded` 状态下正常子系统继续可用，写作规范管理只读，Word 任务提交前和结果区都提示本次未完整应用规范，并提供重新检测和导出脱敏诊断；
- 已确认 `recovery` 状态下前端显示 Adapter 已连接、故障子系统、发生阶段和最近有效备份状态，仅允许重新检测、创建只读备份和导出脱敏诊断，禁止新建、修改、激活配置和提交模型任务；
- `v0.23.1-alpha` 不提供一键重置或一键恢复备份；真实数据恢复必须通过指定已校验备份 ID、二次确认并生成审计记录的显式命令执行。图形化恢复最早在目标机验证稳定后纳入 `v0.24.0-alpha`；
- 已确认模型配置、八类任务映射、激活关系、Key 文件和写作规范数据库构成同一一致性运行数据快照；安装、迁移及显式恢复前必须创建快照，附带版本、数量和校验清单，只能在副本验证通过后整体原子恢复，默认禁止局部文件恢复；
- 快照目录权限为 `0700`，敏感文件为 `0600`；至少保留最近三个已校验快照及上一已验收版本的最后有效快照，唯一有效或仍承担回退作用的快照不得按时间自动删除；清理必须以已有新验证快照为前提并生成不含 Key 明文的审计记录；
- 已确认 Word、Excel、PPT 三个插件、`publish.xml`、Adapter 程序、自启动或当前版本指针及匹配的一致性运行数据快照构成同一发布代际，必须整体验证、切换和回退；禁止混合不同代际后标记安装成功；
- 切换前必须确认 WPS、ET、WPP 均已退出；所有候选文件先在隔离目录验证，再通过持久化事务日志和同文件系统重命名逐项切换。最终健康检查失败或进程中断时，本次或下次安装依据事务日志执行反向补偿，恢复完整上一代际；该机制称为补偿式切换，不宣称跨目录绝对原子；
- 已确认 Python 运行依赖按发布代际隔离：离线 Wheel 安装到版本私有目录，候选导入、预检和正式启动使用同一目录并设置 `PYTHONNOUSERSITE=1`；安装不得修改系统或用户 `site-packages`，回退时同时回退依赖目录；
- 离线 Wheel、锁定依赖清单和私有目录安装结果均需校验；如果目标机没有 `venv`，仍使用版本私有目标目录而不是退回全局安装；
- 已确认安装根目录从 `v0.23.1-alpha` 起分为 `releases/<version>`、`current`、`state`、`backups` 和 `var/{logs,run,transactions}`：程序、脚本、私有依赖和发布清单进入安装后不可修改的版本目录；配置、Key、任务映射和规范库数据库只进入正式 `state`；日志、PID 和事务记录不进入数据快照；
- 从旧版 Adapter 目录迁移到新布局时必须使用写时复制；发布清单记录所需数据结构版本，回退程序时使用与发布代际匹配的已校验快照，不再把运行数据复制回程序目录；
- 已确认从 `v0.23.1-alpha` 起重新组织交付包并采用白名单构建，由安装器、三宿主插件、Adapter、目标 Python Wheel、发布清单、诊断/验收/恢复脚本、必要文档和许可证重新组装，不再复制旧交付包后做增量删除；
- 交付产物排除旧版本包和重复归档、测试与开发脚本、缓存临时文件、现场日志/PID/配置/Key/数据库/备份、被正式入口替代的 standalone 或兼容启动残留、非目标架构或非 Python 3.8 依赖，以及未被清单引用的文档和样例；构建后执行白名单、哈希、引用闭包和敏感信息审计；
- 此次清理只作用于生成的交付产物，不直接删除源码仓库中的历史设计、测试和追溯材料；源码历史删除必须另行评审。

## 6. 当前结论

本地连接失败是三个界面症状的共同上游条件，最终根因是 Python 3.8 不兼容类型注解导致 Adapter 导入崩溃。根因置信度为高。

修复不能只替换单行注解并在开发机通过测试，还必须落实目标 Python 3.8 发布门禁、恢复构建版本策略、事务式升级、降级与恢复状态、旧运行数据保护、发布私有依赖及白名单交付构建。上述决策已经完成共同理解确认，并与全篇文档审查设计合入 Issue #25 统一规格。
